# CI

CI is generated by velnor-actions from `.velnor/config.toml`. Never
hand-edit `.github/workflows/`, `.github/actions/`, `.github/scripts/`,
`.github/velnor/`, `.github/actionlint.yaml` or `.github/AGENTS.md`;
change the config and run `velnor-actions generate`.

## Gates

- **Plan** — computes the job matrix (15-minute timeout; the full
  history checkout is large).
- **Suite (functional)** — a required check (`required = true`):
  `cargo nextest run --workspace --profile functional --no-tests fail`
  (the profile's default filter selects `binary(functional)`). It must
  pass with 0 skipped before merge. It builds the default features, so
  it covers the product-shape journeys only; see the
  [demo feature](#the-demo-feature) below. See
  [functional testing](functional-testing.md) for the CI contract.
- **Rust / junie-tui** and **Rust / jackin-console** — one job per
  default workspace member, built with `--all-features`. Each runs
  `cargo nextest run --profile ci --package <crate> --no-tests fail
  --all-features`, which selects every test target of the package (the
  library, the binaries, `functional` and every other `tests/*.rs`
  target), plus clippy `-D warnings` on `--all-targets`, `cargo fmt
  --check` and `cargo doc`. A new test target needs no CI change. The
  `ci` profile in `.config/nextest.toml` must keep no `default-filter`,
  or targets drop out of this job.
- **Rust / junie-tui (product)** and **Rust / jackin-console
  (product)** — the same five tasks for the product shape. The second
  configuration in `.velnor/config.toml` selects the feature `product`,
  so `jackin-console` gets `--no-default-features --features product`
  (no demo data, no `clap`, no `jackin-preview`). `junie-tui` declares
  `product = ["terminal"]`, so its job builds the library shape that
  jackin consumes (`default-features = false, features = ["terminal"]`):
  `termpane` in, `clap` out. The bins and the `functional` target require
  `cli`, so they are skipped there.
- **Required** — the verdict job. Its `needs` are Plan, the four Rust
  jobs, `suite-functional` and jactionlint, as listed in the generated
  `ci.yml`.
- **DCO** — every commit must carry `Signed-off-by`
  (`git commit -s`, committer Alexey Zhokhov
  <alexey@zhokhov.com>).

## The demo feature

After B1b the feature `demo` is off by default. `Rust / <crate>` runs
with `--all-features` and owns the demo journeys; `Rust / <crate>
(product)` runs `--no-default-features --features product`;
`suite-functional` runs the default features, so it covers the
product-shape PTY journeys only. A demo journey that fails leaves no
terminal-evidence artifact. Run the same commands locally with the
flags above.

The reason is a limit of the generator. `velnor-actions` 0.1.72 gives a
suite no feature field, so `suite-functional` cannot take
`--all-features`. The demo journeys (the `functional` target of
`jackin-console`, which has `required-features = ["demo"]`) therefore
run in `Rust / jackin-console`. The `ci` profile has no default filter,
so that job selects them. The cost is that the failure evidence
artifact and the JUnit report exist only for the suite job, and the
demo journeys now count against the 15-minute crate timeout.

Two configurations in `.velnor/config.toml` produce the jobs: `default`
(`all_features = true`) keeps the existing task ids and check names,
and `product` (`features = ["product"]`) adds the product jobs. The
feature `product` enables nothing; it exists only so the generator can
select the product shape, and no code may test it.

Local equivalents are in [development](development.md). Tool pins
live in `mise.toml`; install with `mise install`.

## Generated workflow check

The pre-commit check validates the staged index. The pre-push check validates
updates to `refs/heads/*` and commit-valued tags under `refs/tags/*`. It skips
deletions, tags that point to trees or blobs, and destinations outside those
namespaces, including notes. Malformed records and unresolved branch or
commit-tag objects fail.

Snapshot files are materialized from Git blobs without checkout filters or
replacement refs. Missing SHA-1 blobs may be hydrated only from the fixed
official GitHub blob API and are checked against their Git object identities.
The generator reads the Velnor, Rust, jactionlint, and ShellCheck pins from the
snapshot, then resolves those tools through the private qualified lock and
cache. It does not run Mise with checkout configuration or trust state.

Run the public checker regression matrix with
`bash tests/check-generated-workflows.sh all`. It uses real Git for snapshot
and ref behavior and controls the external network boundary with deterministic
fixtures. Its valid-snapshot cases stop at the expected bootstrap response; the
matrix does not run private Mise lock/install, Cargo qualification, Velnor, or
the final generated-workflow comparison.

Run `bash tests/check-python-inventory.sh` for the Python runtime inventory's
filesystem checks.

Qualify the actual pinned toolchain and generator by explicitly running
`bash scripts/install-generated-workflow-guard.sh` from reviewed checkout
code. Setup installs and invokes the digest-pinned checker, privately resolves
Mise tools and Cargo dependencies, and runs the real Velnor generator against
the approved seed before it registers hooks. Cold setup requires network
access to the pinned Mise and standalone Python artifacts, GitHub attestation
and API endpoints, the Rust distribution, and locked Cargo sources. Warm
checks select the qualified cache and configure Cargo offline; a selected
snapshot with missing blobs can still use the bounded fixed GitHub API path.
On macOS the real-toolchain harness runs two warm public hooks under
`sandbox-exec` with networking denied and first confirms that a curl control
request is denied. On other hosts, the caller must enforce or observe a
no-egress boundary to qualify offline behavior.

After setup, run `bash tests/check-installed-generated-workflow-guard.sh` to
exercise real installed hooks with the qualified Mise/Velnor artifacts. It
uses a shallow source without the approved seed commit, checks `git commit
--only`, linked and split indexes, matching commit and push cases, and confirms
that staged workflow drift is rejected by the real Velnor comparison. It also
checks installed-cache integrity and refuses a foreign hook. The harness
preserves logs and manifests when `BASELINE_GUARD_EVIDENCE_DIR` names an output
directory; its evidence records whether network isolation was enforced by the
harness.

The redirect regression uses a deterministic curl boundary. The HTTP downgrade
URL appears only in a synthetic HTTPS response's `Location` header; the test
asserts that the URL never appears in the request log and that only the
initial HTTPS request occurred. It does not send cleartext HTTP traffic.

## Workflow policy boundary

The generated CI workflow runs the Velnor generation and diff check for the
workflow files present in the branch. That check establishes reproducibility;
it does not authorize changes to `.velnor/config.toml` or to the generated CI
policy. Local hooks can be absent or bypassed, and a branch can change its own
workflow before CI evaluates it. GitHub settings inspection on 2026-11-06
found no branch-protection rule and no repository ruleset requiring a trusted
workflow. The repository owner must configure a required trusted workflow or
ruleset for server-side enforcement. Until then, workflow-source and policy
changes need trusted review.
